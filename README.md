# Event Booking API

![Go](https://img.shields.io/badge/Go-1.26-00ADD8?logo=go&logoColor=white)
![Gin](https://img.shields.io/badge/Gin-1.12-008ECF)

![JWT](https://img.shields.io/badge/auth-JWT-black?logo=jsonwebtokens)

A REST API for booking events, written in **Go** with the **Gin** framework and an embedded **SQLite** database.

Anyone can browse events. Registered users can create their own events, edit or delete the events they created, and sign up for (or cancel their registration for) any event. Protected routes are secured with JWT, and passwords are stored as bcrypt hashes.

## Features

- Full CRUD for events: list, get by ID, create, update, delete
- User signup and login
- Passwords hashed with bcrypt before they are stored
- JWT authentication (HS256, tokens valid for 2 hours) implemented as a Gin middleware
- Ownership check: only the user who created an event can update or delete it
- Registration for an event and cancellation of a registration
- Versioned API: every endpoint lives under `/api/v1`
- Meaningful HTTP status codes: `404` for missing resources, `403` for actions on someone else's event, `409` for duplicates
- Configuration through environment variables or a `.env` file
- CORS support so a browser frontend on another origin can call the API
- SQLite database that is created automatically on first start, with no external services to install
- Request validation: all event and user fields are required, the email must be valid, the password must be 8 to 72 characters long, and events cannot be created, moved or booked in the past
- Validation errors name the problem, e.g. `{"message": "Password must be at least 8 characters long."}`
- Events are listed in date order, the soonest first
- Interactive API documentation with Swagger UI at `/swagger/index.html`
- A seed command that fills an empty database with sample users, events and registrations
- A ready-to-run `.http` scenario that exercises every endpoint and its error cases

## Getting started

### Prerequisites

- [Go](https://go.dev/dl/) 1.26 or newer (the version declared in `go.mod`)

No database server and no C compiler are needed: the SQLite driver is pure Go.

### Run locally

1. Clone the repository and download the dependencies:

   ```bash
   git clone https://github.com/lilvload/event-booking-api.git
   cd event-booking-api
   go mod download
   ```

2. Create your own `.env` file from the template:

   ```bash
   cp .env.example .env        # Windows PowerShell: copy .env.example .env
   ```

3. Open `.env` and set `JWT_SECRET`. Generate a random value, for example in Git Bash:

   ```bash
   openssl rand -hex 32
   ```

4. Start the server:

   ```bash
   go run .
   ```

The server starts on `http://localhost:8080` (or the port set in `PORT`), and the API is served under `http://localhost:8080/api/v1`. On first start it creates the SQLite database file (`api.db` by default) together with all tables.

The interactive API documentation is then available at `http://localhost:8080/swagger/index.html`.

If `JWT_SECRET` is missing, the server stops with an error message on startup.

### Sample data

A fresh database is empty. To fill it with sample data, run from the project root:

```bash
go run ./cmd/seed
```

It creates 3 users, 8 events (6 upcoming, 2 in the past, dates relative to today) and 7 registrations in the database set by `DB_PATH`. All sample users have the password `password123`:

| Email | Owns events |
|-------|-------------|
| `alice@example.com` | Go meetup, Frontend workshop, Database design basics |
| `bob@example.com` | Startup pitch night, Hackathon: Smart City, Board games evening |
| `carol@example.com` | Design systems talk, Book club: Clean Code |

The seed only fills an empty database: if the database already has users, it stops without changing anything. To reset the data, stop the server, delete the database file and run the seed again. Use it for development only, never on a production database.

### Build a binary

```bash
go build -o bin/event-booking-api .
./bin/event-booking-api
```

Run the binary from the folder that contains `.env`, or set the variables in the system environment.

To start from an empty database, stop the server and delete the database file.

## Configuration

Settings are read from environment variables. On startup the server loads them from a `.env` file in the working directory, if one exists. Variables already set in the system environment take precedence over the file, so on a hosting platform you set them in its dashboard and no `.env` file is needed.

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `JWT_SECRET` | **Yes** | none | Secret key used to sign and verify JWTs. Use a long random value and never commit it. |
| `PORT` | No | `8080` | Port the HTTP server listens on |
| `DB_PATH` | No | `api.db` | Path to the SQLite database file |
| `CORS_ALLOWED_ORIGINS` | No | `http://localhost:5173` | Comma-separated list of frontend origins allowed to call the API, without spaces, e.g. `http://localhost:5173,https://my-app.com` |

`.env` is listed in `.gitignore` and must never be committed. `.env.example` is committed and lists every variable the project expects. When you add a new variable, add it to `.env.example` too.

Changes to `.env` take effect after the server is restarted.

Other settings are still defined in the code:

| Setting | Value | Location |
|---------|-------|----------|
| Connection pool | 10 open / 5 idle connections | `db/db.go` |
| Token lifetime | 2 hours | `utils/jwt.go` |
| bcrypt cost | 12 | `utils/hash.go` |

Gin runs in debug mode by default. Set `GIN_MODE=release` to turn off debug logging.

## Frontend integration

The frontend lives in its own project with its own `.env`. For a Vite app it typically contains:

```env
VITE_API_URL=http://localhost:8080/api/v1
```

With the version in the base URL, the frontend code uses short paths such as `` `${API_URL}/events` ``, and moving to a future `v2` means changing this one line.

To make the two projects work together locally:

1. Start this API (see [Run locally](#run-locally)).
2. Make sure the frontend's origin, e.g. `http://localhost:5173`, is listed in `CORS_ALLOWED_ORIGINS` in the API's `.env`. Otherwise the browser blocks the requests with a CORS error.
3. Point the frontend at the API URL (`VITE_API_URL` above).

The API allows the `GET`, `POST`, `PUT`, `DELETE` and `OPTIONS` methods and the `Origin`, `Content-Type` and `Authorization` headers from the allowed origins.

Never put secrets such as `JWT_SECRET` in the frontend `.env`: variables there are bundled into the JavaScript that every visitor downloads.

## Authentication

1. Create an account with `POST /signup`.
2. Log in with `POST /login` to receive a JWT.
3. Send the token in the `Authorization` header of every protected request.

```
Authorization: Bearer <your-jwt-token>
```

The `Bearer ` prefix is optional: the raw token without the prefix is accepted too. A missing, invalid or expired token results in `401 Unauthorized`.

Tokens are signed with `JWT_SECRET`. If the secret changes, all previously issued tokens stop working and users have to log in again.

## API documentation (Swagger)

With the server running, open `http://localhost:8080/swagger/index.html`. Swagger UI lists every endpoint with its parameters, request body and responses, and lets you send requests from the browser:

1. Run `POST /login` with **Try it out** → **Execute** and copy the `token` from the response.
2. Click **Authorize** and enter `Bearer <token>`.
3. Protected endpoints now send the token automatically.

The raw OpenAPI (Swagger 2.0) description is served at `/swagger/doc.json` and is also stored in `docs/swagger.json` and `docs/swagger.yaml`. Frontend tools can generate TypeScript types or API clients from it.

### Updating the documentation

The documentation is generated from the `// @...` comments above `main()` in `main.go` and above each handler in `routes/`. After changing a route or its comments, regenerate it and commit the `docs/` folder together with the code:

```bash
go install github.com/swaggo/swag/cmd/swag@v1.16.4   # once
swag init
```

The version of the `swag` command must match the `github.com/swaggo/swag` version in `go.mod`. Otherwise the generated `docs/docs.go` may not compile (for example, `unknown field LeftDelim`). Check both with `swag --version` and `go list -m github.com/swaggo/swag`.

## API reference

Base URL: `http://localhost:8080/api/v1`

All endpoint paths below are relative to the base URL: `POST /login` means `POST http://localhost:8080/api/v1/login`. The same information is available interactively in [Swagger UI](#api-documentation-swagger), which sends requests to the correct base URL by itself.

| Method | Endpoint | Description | Auth |
|--------|----------|-------------|------|
| `GET` | `/events` | List all events | No |
| `GET` | `/events/:id` | Get a single event | No |
| `POST` | `/events` | Create an event | Required |
| `PUT` | `/events/:id` | Update an event | Required (creator only) |
| `DELETE` | `/events/:id` | Delete an event | Required (creator only) |
| `POST` | `/events/:id/register` | Register the current user for an event | Required |
| `DELETE` | `/events/:id/register` | Cancel the current user's registration | Required |
| `POST` | `/signup` | Create a user | No |
| `POST` | `/login` | Log in and receive a JWT | No |

Request and response bodies are JSON with camelCase field names (`name`, `dateTime`, `userId`).

All error responses have the form `{"message": "..."}`. For a validation error the message names the problem, for example `"Invalid email format."` or `"Password must be at least 8 characters long."`.

### Versioning

The version in the path changes only for breaking changes: renaming or removing a field or an endpoint, changing a field's type or the shape of a response, making an optional field required, or changing a status code that clients rely on. New endpoints and new response fields are added to `v1` without a version change.

When a breaking change is needed, it goes into a new `/api/v2` group next to `/api/v1`, and both versions are served until no client uses `v1` any more. Swagger UI (`/swagger/index.html`) stays outside the versioned paths.

### Users

#### `POST /signup`

```json
{
  "email": "user@example.com",
  "password": "password123"
}
```

`email` must be a valid email address. `password` must be 8 to 72 characters long (bcrypt ignores everything after 72 bytes).

| Status | Body |
|--------|------|
| `201 Created` | `{"message": "User created successfully!"}` |
| `400 Bad Request` | A field is missing, the email is invalid, the password is too short or too long, or the JSON is invalid |
| `409 Conflict` | `{"message": "Email already registered."}` |
| `500 Internal Server Error` | The user could not be saved |

#### `POST /login`

Takes the same body as `/signup`. The password length is not checked here, so a wrong password of any length gets `401`.

```json
{
  "message": "Login successful!",
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

| Status | Body |
|--------|------|
| `200 OK` | Message and token |
| `400 Bad Request` | A field is missing, the email is invalid or the JSON is invalid |
| `401 Unauthorized` | `{"message": "Incorrect email or password"}` |
| `500 Internal Server Error` | The token could not be generated |

### Events

#### Event object

```json
{
  "id": 1,
  "name": "Go meetup",
  "description": "Talks",
  "location": "Kyiv",
  "dateTime": "2026-12-01T18:00:00Z",
  "userId": 1
}
```

`userId` is the ID of the user who created the event. It is taken from the token, not from the request body.

#### `GET /events`

Returns `200 OK` with an array of event objects sorted by `dateTime`, the soonest first, or an empty array `[]` when there are no events yet.

#### `GET /events/:id`

| Status | Body |
|--------|------|
| `200 OK` | Event object |
| `400 Bad Request` | The ID is not a number |
| `404 Not Found` | `{"message": "Event not found."}` |
| `500 Internal Server Error` | The event could not be fetched |

#### `POST /events`

All four fields are required. `dateTime` must be an RFC 3339 timestamp in the future.

```json
{
  "name": "Go meetup",
  "description": "Talks",
  "location": "Kyiv",
  "dateTime": "2026-12-01T18:00:00.000Z"
}
```

| Status | Body |
|--------|------|
| `201 Created` | `{"message": "Event created!", "event": { ... }}` |
| `400 Bad Request` | A field is missing, the JSON is invalid, or `dateTime` is in the past |
| `401 Unauthorized` | No valid token |
| `500 Internal Server Error` | The event could not be saved |

#### `PUT /events/:id`

Takes the same body as `POST /events`; all fields are required, so this is a full replacement. The new `dateTime` must be in the future.

| Status | Body |
|--------|------|
| `200 OK` | `{"message": "Event updated successfully!"}` |
| `400 Bad Request` | Invalid ID or request body, or `dateTime` is in the past |
| `401 Unauthorized` | No valid token |
| `403 Forbidden` | The current user is not the creator of the event |
| `404 Not Found` | `{"message": "Event not found."}` |
| `500 Internal Server Error` | The event could not be fetched or updated |

#### `DELETE /events/:id`

| Status | Body |
|--------|------|
| `200 OK` | `{"message": "Event deleted successfully!"}` |
| `400 Bad Request` | Invalid ID |
| `401 Unauthorized` | No valid token |
| `403 Forbidden` | The current user is not the creator of the event |
| `404 Not Found` | `{"message": "Event not found."}` |
| `500 Internal Server Error` | The event could not be fetched or deleted |

### Registrations

#### `POST /events/:id/register`

No request body. Registers the user identified by the token. Events that have already started cannot be booked.

| Status | Body |
|--------|------|
| `201 Created` | `{"message": "Registered!"}` |
| `400 Bad Request` | Invalid ID, or `{"message": "Cannot register for an event in the past."}` |
| `401 Unauthorized` | No valid token |
| `404 Not Found` | `{"message": "Event not found."}` |
| `409 Conflict` | `{"message": "Already registered for this event."}` |
| `500 Internal Server Error` | The registration could not be saved |

#### `DELETE /events/:id/register`

No request body.

| Status | Body |
|--------|------|
| `200 OK` | `{"message": "Cancelled!"}` |
| `400 Bad Request` | Invalid ID |
| `401 Unauthorized` | No valid token |
| `404 Not Found` | `{"message": "Registration not found."}` (the user is not registered for this event) |
| `500 Internal Server Error` | The registration could not be cancelled |

## Database schema

Three tables are created automatically in the database file (`DB_PATH`, `api.db` by default):

| Table | Columns |
|-------|---------|
| `users` | `id` (PK, autoincrement), `email` (unique, not null), `password` (bcrypt hash, not null) |
| `events` | `id` (PK, autoincrement), `name`, `description`, `location`, `dateTime` (all not null), `user_id` → `users.id` |
| `registrations` | `id` (PK, autoincrement), `event_id` → `events.id` (cascade delete), `user_id` → `users.id` (cascade delete), unique pair `(event_id, user_id)` |

```
users 1 ──── * events
users 1 ──── * registrations * ──── 1 events
```

## Testing the API

The quickest way to try the endpoints is [Swagger UI](#api-documentation-swagger) in the browser.

To check the whole API after a change, use [`api-test/test-all.http`](api-test/test-all.http). It is a scenario of 32 requests that covers every endpoint together with its error cases, including validation (invalid email, short password, dates in the past): two users sign up and log in, user A creates, updates and deletes an event, user B tries to change it and registers for it.

1. Install the [REST Client](https://marketplace.visualstudio.com/items?itemName=humao.rest-client) extension for VS Code. The file uses its syntax for passing values between requests, so other HTTP clients will not run it as is.
2. Start the server, preferably with an empty database: set `DB_PATH=test.db` in `.env` and delete `test.db` before each run.
3. Open the file and click **Send Request** above each request, from top to bottom. Later requests take the tokens and the event ID from the responses of earlier ones, so nothing has to be copied by hand.
4. Compare the response status with the one written above the request.

Run against a database that already has the test users, steps 2 and 4 return `409`; the rest of the scenario still works.

There are no automated tests yet.
